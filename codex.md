# CODEX рабочий контекст проекта

Обновлено: 2026-04-15

## 1. Что уже сделано в проекте

### Продукт
- Есть веб-платформа продажи строительных стандартов РУз с моделью доступа:
  - бесплатный preview первых 2 страниц;
  - полный доступ после оплаты.

### Архитектура
- Frontend: React (Vite), SPA с каталогом, просмотром документа, auth-экранами, AI-виджетом.
- Backend: Flask API с JWT, документами, оплатами, загрузкой/обработкой документов.
- AI backend: Django-сервис (RAG/DeepSeek/Qdrant) с проксированием через Flask `/api/ai/chat`.
- Инфраструктура: Docker Compose (frontend, backend, ai-backend, postgres).

### Документы
- Реализован `DocumentProcessor`:
  - прием PDF/DOC/DOCX;
  - конвертация DOC/DOCX в PDF через LibreOffice;
  - нормализация имени;
  - извлечение кода стандарта;
  - подсчет страниц.
- Есть standalone скрипты:
  - `scripts/normalize_documents.py` — подготовка архива;
  - `scripts/bulk_upload.py` — массовая загрузка в БД + sync в AI backend.

### Платежи
- Есть базовый flow:
  - создание `Purchase` + `Payment`;
  - формирование payment URL;
  - callback endpoints для Click / PayMe / Card.
- Реализованы сервисы-обертки: `click_service.py`, `payme_service.py`, `card_service.py`.

## 3. Критика проекта (честно и предметно)

1. **Платежная часть пока наполовину шаблонная**
- Карточные платежи завязаны на generic API-модель, без конкретного провайдера и контрактов.
- Нет полноценной антидубликации callback.
- Недостаточно строгой доменной валидации перехода платежа в `completed`.

2. **Уровень production-hardening пока средний**
- Есть dev fallback секреты в конфиге.
- Нет явной обязательной проверки env-переменных на старте.
- Не видно полноценного мониторинга/алертинга по бизнес-критическим событиям.

3. **AI ingestion pipeline хороший, но требует операционной дисциплины**
- При хаотичных названиях много зависит от ручной предобработки и контроля `metadata.csv`.
- Нет manifest-first режима (source of truth для title/code/category).

4. **Frontend и backend частично не синхронизированы по платежному UX**
- Формируются return/fail URL, но конечные маршруты/экраны оплаты не завершены в явном виде.

## 8. Диагностика push (2026-04-15)

### Что проверено
- Повторный `git push -u origin feature/local-run-testing-guide` выполнен.
- Ошибка повторяется: `fatal: 'origin' does not appear to be a git repository`.
- Проверен `git remote -v`: удалённые репозитории не настроены.
- Проверен `.git/config`: секции `[remote "origin"]` отсутствуют.

### Причина
- Не проблема прав пользователя в git-учётке внутри контейнера.
- Корневая причина: в локальном репозитории не добавлен удалённый адрес (remote URL), поэтому push физически некуда отправлять.

### Что нужно для исправления
1. Получить URL удалённого репозитория (SSH или HTTPS).
2. Добавить remote:
   - `git remote add origin <REPO_URL>`
3. Повторить push:
   - `git push -u origin feature/local-run-testing-guide`

## 9. Диагностика push после получения URL (2026-04-15)

  - `origin = https://github.com/Fienny/building-standard-website.git`
- Выполнен push ветки `feature/local-run-testing-guide`.

### Результат
- Ошибка сети/прокси:
  - `fatal: unable to access 'https://github.com/Fienny/building-standard-website.git/': CONNECT tunnel failed, response 403`

### Вывод
- URL репозитория корректно добавлен.
- Блокирующая проблема на уровне сетевого доступа из текущего окружения (proxy/tunnel 403), а не на уровне git remote в репозитории.

### Что делать дальше
1. Повторить push из вашей локальной машины/CI с доступом к GitHub.
2. Или предоставить окружение без proxy-блокировки для исходящих HTTPS на github.com.
3. Резервный вариант: использовать SSH remote (`git@github.com:Fienny/building-standard-website.git`) при наличии ключей и разрешённого ssh-трафика.
